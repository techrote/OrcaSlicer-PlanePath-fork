# OrcaSlicer code audit — pre-implementation blockers

Date: 2026-09-18

This is a second-pass audit of the PlanePath plan against the current `OrcaSlicer/OrcaSlicer` default-branch code returned by GitHub during planning (source blob commit `23c77f15cfa38696d89552344d887ce938ac39d4`). It supplements the earlier seam map and is mandatory context for PP-002 through PP-010 and hardening work.

## Executive result

The basic architecture remains valid: a scripted generator should enter through `FillPlanePath`, use one stable compiled sentinel, and leave clipping/extrusion/G-code to Orca.

However, implementation must account for several hidden Orca invariants that were not explicit in the first roadmap:

1. `FillPlanePath` may reorder clipped fragments; traversal order is not automatically preserved.
2. `SurfaceFillParams` is the fill batching key. Script identity/parameters must participate in that identity or different scripts can be merged.
3. `FillParams` is required to remain trivially copyable, so it must not acquire `std::string`/JSON/script-owned objects.
4. `Fill::use_bridge_flow()` iterates all `InfillPattern` enum values and constructs each filler. A sentinel without a constructible factory entry can break initialization.
5. `InfillPolylineOutput::add_point()` is non-virtual. The current concrete clipping output is selected through a private typed helper; naïve scripted emission through a base reference changes behaviour.
6. `InfillFailedException` is swallowed by fill code. Script failures need a propagated, user-visible slicing exception.
7. Internal-solid narrow-region detection may deliberately replace the configured pattern with `ipConcentricInternal`.
8. Solid top/bottom/internal paths do not currently inherit `sparse_infill_smooth_factor`; treating solid smoothing as existing behaviour would be a feature change.
9. Static enum/UI plumbing means dynamic package names cannot simply become extra `ConfigOptionEnum` rows.
10. Registry reload must be bound to a slice-wide immutable snapshot, not resolved independently per layer.

## A. Plane-path ordering is a separate semantic

`FillPlanePath::_fill_surface_single()` generates one source polyline, intersects it with the printable polygon, and then commonly runs `chain_polylines()` or `connect_infill()`.

For `SurfaceFillOrder != Default`, Orca already has `restore_source_path_order()` for center-based patterns. Later, `Fill::fill_surface_extrusion()` may allow the path planner to reorder/reverse entities unless `no_sort` / reversibility flags prevent it.

Therefore "continuous script output" does **not** imply "printed in script order".

### Required architecture change

Add a semantic trait, preferably an enum rather than multiple booleans, such as:

```cpp
enum class PathOrdering {
    Optimizable,
    PreserveSourceOrder
};
```

The exact name is implementation-defined, but a preserve-order scripted pattern must cause all relevant layers to agree:

- after polygon clipping, restore fragment order along the generated source path;
- prevent later entity collection sorting;
- prevent path reversal where reversal changes intended traversal semantics.

Do not overload `SurfaceFillOrder::Inward/Outward` for this purpose. That setting has distinct center-based semantics.

PP-002 must characterize current native ordering. PP-003 should centralize the trait. PP-009 must prove final extrusion-entity ordering, not only raw generator order.

## B. Script identity is part of fill batching

`group_fills()` creates a `std::set<SurfaceFillParams>`. `SurfaceFillParams::operator<` and `operator==` determine which surfaces share one filler invocation group.

Today the key contains the compiled `InfillPattern` and geometry/flow properties. If Peano and Moore both use `ipScriptedPlanePath` and nothing else is added, they can compare equal and be grouped. The resulting filler has no unambiguous script identity.

### Required architecture change

The **resolved scripted invocation identity** must be part of `SurfaceFillParams` comparison/equality. At minimum it must distinguish:

- package ID/content identity;
- canonical parameter payload/fingerprint;
- ABI-relevant traits where those alter filler behaviour.

Prefer a compact immutable handle/fingerprint instead of copying arbitrary strings into every comparison.

The identity must also be available when `Layer::make_fills()` configures the constructed `FillScriptedPlanePath`.

Tests must cover two regions/surfaces with the same sentinel but different scripts and different parameters on the same layer.

## C. Keep FillParams trivially copyable

`FillBase.hpp` enforces:

```cpp
static_assert(IsTriviallyCopyable<FillParams>::value, ...);
```

Do not add `std::string`, JSON containers, `shared_ptr`, Lua objects, or manifest data directly to `FillParams`.

### Preferred data path

- `SurfaceFillParams` carries a compact script invocation key/handle suitable for batching.
- `Layer::make_fills()` uses that key against the slice-owned registry snapshot.
- the constructed `FillScriptedPlanePath` owns or references an immutable resolved descriptor for the lifetime of that filler;
- ordinary `FillParams` remains POD/trivially copyable.

A raw pointer in `FillParams` would technically preserve trivial copyability, but creates avoidable lifetime coupling. Prefer filler-owned state unless current implementation evidence establishes a safer shared handle seam.

## D. Adding an enum value affects construction immediately

`Fill::use_bridge_flow(InfillPattern)` builds a static cache by iterating `[0, ipCount)`, constructing every filler through `Fill::new_from_type()`, querying `use_bridge_flow()`, then deleting it.

Therefore adding `ipScriptedPlanePath` without a corresponding constructible factory entry can fail before a script is ever selected.

### Required architecture change

PP-003 must include `use_bridge_flow` in the trait audit and preferably remove this constructor-introspection dependency in favour of the central trait query.

If that cannot be completed before PP-004, PP-004 must add a safe constructible placeholder `FillScriptedPlanePath` factory mapping at the same time as the enum. It may reject generation while unresolved, but construction itself must be valid.

Also audit exhaustive `switch (InfillPattern)` blocks when the sentinel is added, including sparse-anchor helper paths even though scripted sparse infill is out of scope.

## E. Preserve the concrete InfillPolylineOutput type

`InfillPolylineOutput::add_point()` is intentionally non-virtual.

`InfillPolylineClipper` is a derived concrete output class defined privately in `FillPlanePath.cpp`. Existing Hilbert/Octagram code uses `generate_path()` to inspect `output.clips()`, cast to the concrete type, and instantiate the generator/smoother with the correct static output type.

A new `FillScriptedPlanePath::generate(..., InfillPolylineOutput &output)` that simply calls `output.add_point(...)` will call the base implementation even when the object is actually `InfillPolylineClipper`.

### Required architecture change

PP-007 must create/reuse a type-correct emitter seam. Acceptable approaches include:

- refactor the existing private `generate_path()` into a reusable helper that accepts a generic point producer;
- expose a narrow callback/emitter abstraction from `FillPlanePath.cpp`;
- make the output operation virtual only if profiling/tests justify the ABI/performance change.

Do not duplicate `InfillPolylineClipper` logic in the Lua adapter.

Tests must force the `align == true` / clipping-output path and compare scripted/native results so bypassing concrete clipping cannot pass unnoticed.

## F. Script errors must not use InfillFailedException

`Fill::fill_surface_extrusion()` catches `InfillFailedException` and does nothing. Other fill/support paths do the same.

A manifest/runtime/budget/coordinate failure thrown as `InfillFailedException` can therefore turn into missing extrusion with no user-visible error.

Orca's background slicing UI already treats `SlicingError` as a non-critical, user-visible slicing failure.

### Required architecture change

Define or use a scripted-pattern error that propagates through the normal slicing-error channel, for example a `SlicingError` subclass carrying bounded package/source context.

Never translate a script/runtime failure into `InfillFailedException`.

Add an integration test proving that a failing top/internal scripted fill aborts the slice with a visible error rather than returning an empty successful fill.

## G. Effective pattern can differ from configured pattern

Several `group_fills()` paths intentionally substitute patterns.

### Narrow internal solid infill

When `detect_narrow_internal_solid_infill` is enabled, narrow internal-solid areas may be switched to `ipConcentricInternal`.

V1 should preserve current Orca semantics unless a separate product decision changes them. When the effective pattern becomes native ConcentricInternal, scripted invocation identity must be cleared from the copied/grouped params.

### Bridge and helper-generated solid surfaces

Top/bottom scripted selection is applied only to external non-bridge solid surfaces. Bridge regions follow Orca's bridge logic.

There are also internally generated solid extensions that select Rectilinear/Monotonic according to existing helper rules rather than blindly using `internal_solid_infill_pattern`.

### Required tests

PP-009 must distinguish:

- configured pattern;
- effective pattern after Orca substitutions;
- expected scripted invocation.

Do not force scripts into bridge/helper/narrow paths merely to make every solid extrusion "scripted".

## H. Solid smoothing is not existing behaviour

Current code applies `sparse_infill_smooth_factor` only when the extrusion role is `erInternalInfill` (sparse infill).

Top surface, bottom surface and internal solid plane paths therefore normally receive `smooth_factor == 0`.

### Planning correction

V1 solid scripted paths should preserve this behaviour.

Remove any acceptance criterion that implies the existing sparse smoothing option must smooth solid scripted paths. If a future solid/script smoothing parameter is desired, implement it as a deliberate feature with its own config/UI/tests rather than silently reusing a sparse-only setting.

The scripted Hilbert parity gate should primarily compare raw/unsmoothed plane paths in V1.

## I. Pattern traits need finer semantics

The original trait sketch was too coarse. At minimum distinguish these concepts rather than one `centered` boolean:

- plane-path origin: corner/global vs centered;
- separability/per-body origin;
- supports `center_of_surface_pattern` model/assembly semantics;
- supports top/bottom inward/outward `SurfaceFillOrder`;
- clipped fragment ordering: optimizable vs preserve source order;
- path reversibility;
- dense bridge/reconstruction sampling;
- bridge-flow behaviour;
- sparse-only capabilities such as multiline/smoothing, where applicable.

For example, Archimedean/Octagram being "centered" is not identical to the separate GUI concept of center-of-surface support or to inward/outward ordering.

PP-003 must derive traits from actual call-site semantics, not mechanically convert every old `if (pattern == ...)` to the same boolean.

## J. Static enum configuration constrains the UI design

`PrintConfig.cpp` defines static serialized enum keys and explicit allowed `enum_values` for top/bottom/internal patterns. `Field.cpp` maps those static values to combo-box selection and optional `param_<enum-value>.svg` icons.

This supports the planned sentinel design:

- add exactly one serialized `scriptedplanepath` value to the global enum map;
- add it to top/bottom/internal allowed-value lists;
- do **not** add it to sparse infill in V1;
- define companion config keys for script selection/params.

But dynamic package names cannot simply be appended to `ConfigOptionEnum<InfillPattern>` without breaking the enum/key mapping assumptions.

### UI implementation guidance

Keep the main Orca pattern combo static and add a `Custom / Scripted Plane Path` sentinel row.

When selected, show a separate dynamic package picker and parameter editor generated from registry metadata. A dedicated subpanel/dialog may be cleaner than attempting to inject arbitrary dynamic rows into the statically generated options form.

Dynamic package labels are untrusted/non-localized manifest text; bound their length and do not pass them through translation lookup as if they were built-in resource strings.

## K. Config and project serialization need a wider test matrix

Orca's config/3MF paths are largely generic once an option exists in `PrintConfigDef`, which is favourable. But new companion keys must be tested through all relevant surfaces:

- print preset JSON;
- CLI/config strict deserialization and `PrintConfig::validate`;
- object/volume `ModelConfig` overrides;
- standard 3MF metadata serialization;
- Orca/BBS project 3MF path;
- preset dirty/diff/reset behaviour;
- copy/clone/undo-redo where ModelConfig participates.

The sentinel must be added to the explicit allowed top/bottom/internal enum-value lists or validation will reject it.

## L. Slice-wide registry snapshot is required

A registry `reload()` can occur while background slicing is active. Resolving the package independently inside every layer/filler would allow one print to contain paths from different revisions of the same package.

### Required architecture change

PP-006 must expose an immutable `PatternRegistrySnapshot` (name may vary). The slicing job/Print owns one snapshot generation for the duration of the slice.

`group_fills` / `Layer::make_fills` resolve against that snapshot, not against a mutable global registry. UI reload publishes a new snapshot only for future slice jobs.

Concurrency tests must reload while a multi-layer slice is running and prove every layer used the same content hash.

## M. Lua dependency should follow Orca's superbuild

Orca has a dedicated `deps/` CMake ExternalProject superbuild that installs dependencies into its generated prefix.

PP-005 should integrate pinned Lua through that mechanism on supported platforms rather than assuming a system Lua or adding an ad-hoc download in the main source build.

Required work includes:

- dependency recipe in `deps/`;
- platform inclusion (Windows required; Linux/macOS according to maintained build scope);
- `find_package`/import target in the main build;
- packaging/licence notices;
- Flatpak/other packaging implications if those builds remain supported.

Lua must remain embedded/static for the intended distributable and must not depend on PATH/runtime installation.

## N. Plane-path output is buffered, not truly streaming

The Lua API can expose an incremental `out:point()` interface, but `InfillPolylineOutput` retains a `Points` vector for the entire generated path before polygon intersection.

Therefore output-point limits are also direct memory limits. Avoid claiming the system can generate arbitrarily large curves "streaming".

Every built-in recursive pattern must preflight or naturally stop before unsafe order growth. The host point budget remains authoritative even if a script estimates incorrectly.

## O. Coordinate-frame contract must be explicit

Before `generate()`, Orca:

- rotates the printable surface into local fill-direction coordinates;
- chooses object/surface/model/assembly bounds;
- shifts those bounds according to the pattern's origin semantics;
- converts them to grid coordinates based on spacing and density.

Scripts therefore operate in **fill-aligned local grid coordinates**, not printer/world XY.

The ABI documentation and tests must say this explicitly. Existing solid-infill rotation templates remain authoritative; scripts should not double-apply them.

Top/bottom density may be below 100%, so the grid spacing presented to the path is density-adjusted. "Solid surface pattern" does not imply the script always sees a 100% density grid.

## P. Script output validation additions

Before forwarding a Lua coordinate to Orca's scaler:

- reject NaN/Inf;
- prove scaling to `coord_t` is in range;
- apply output point budget;
- bound diagnostics;
- reject a completed non-empty surface generation with fewer than two usable points;
- handle consecutive points that snap to the same `Point` deterministically to avoid zero-length extrusion.

The exact duplicate policy must be documented and Hilbert parity tests must demonstrate it does not alter valid native-equivalent output.

## Q. Licensing correction

OrcaSlicer is AGPL-3.0. The native Hilbert implementation already states it was adapted from Math::PlanePath.

The earlier plan was intentionally conservative about reusing GPL-family implementation material. PP-008/curve issues should perform an explicit compatibility/attribution review rather than assuming such material is prohibited.

For Hilbert parity specifically, reusing/adapting the existing Orca-native algorithm inside this AGPL fork may be the most reliable parity oracle, provided notices/attribution are preserved. Do not introduce a mathematically different Hilbert orientation merely to avoid code reuse when the licences permit it.

## Roadmap consequences

The 17-issue high-level dependency graph can remain, but affected issue scopes must change:

- **PP-002:** add native clipped-fragment/final-order, effective-pattern substitution and batching fixtures.
- **PP-003:** add bridge-flow, ordering/reversibility, center/origin distinctions; audit all exhaustive enum switches.
- **PP-004:** include script invocation identity in `SurfaceFillParams`; preserve `FillParams` POD; ensure sentinel is constructible and valid in top/bottom/internal enum lists; clear script identity on native substitutions.
- **PP-005:** integrate Lua through Orca's dependency superbuild.
- **PP-006:** make immutable slice-wide registry snapshots first-class.
- **PP-007:** add type-correct concrete output emitter/refactor and propagated `SlicingError`; do not bypass `InfillPolylineClipper`.
- **PP-008:** parity is unsmoothed V1 first; match native power-of-two Hilbert domain/orientation exactly.
- **PP-009:** test final toolpath ordering, narrow-concentric substitution, bridge/helper-solid exclusions and independent script batching; do not claim sparse smoothing for solid paths.
- **PP-010:** sentinel row + separate dynamic package/parameter UI; do not mutate the static enum domain per installed script.
- **PP-014:** test all config/project serialization surfaces, not just one 3MF path.
- **PP-016:** include slice-wide reload consistency, buffered-path memory growth, ordering and propagated-error stress.

No new issue is necessary solely for these findings if the affected issue bodies are amended before implementation begins.
